Case Studies

Real migrations, refactors, and lessons from 10+ years across healthcare, e-commerce, and booking platforms.

CASE 01 Java 6 → Java 21: modernizing a legacy monolith at HealthAsyst
// problem

A large enterprise application had been running on Java 6 for years — well past its supported life, missing modern JVM performance and security improvements, and written in a style (verbose boilerplate, nested loops, manual iteration) that made it slow to extend and hard to reason about. It also existed as a single deployable monolith, which meant even small changes carried the risk and overhead of a full redeploy.

// approach

Led the migration from Java 6 to Java 21 LTS, working through the usual pain points of that jump: replacing APIs deprecated or removed across major versions, rewriting Java-6-era loop and collection patterns with the Stream API and lambdas, and eliminating nested loops and other O(n²)-style patterns in favor of more efficient algorithms. In parallel, split the single monolith into multiple independent Spring Boot services organized by business capability — not true microservices, since all services still share one underlying database, but enough separation to deploy and scale pieces of the system independently.

// result

A codebase running on a currently supported LTS release, measurably leaner after removing inefficient loop and object-handling patterns, and now deployable service-by-service instead of as one large release. Recently concluded work.

CASE 02 AngularJS → React: aligning the frontend stack across the client's platforms
// problem

The client's other web applications had already standardized on React, leaving this AngularJS app as the odd one out — harder to staff, harder to share components across, and increasingly out of step with the client's engineering direction. Leadership made the call to bring it in line with the rest of the portfolio.

// approach

Rebuilt the application's component architecture around React's model, which meant working through the typical friction points of an AngularJS-to-React move: replacing two-way `$scope` data binding with explicit, unidirectional state management; converting AngularJS directives and controllers into reusable React components; swapping AngularJS's built-in dependency injection and services for React patterns (hooks/context); and re-implementing routing and filters/pipes with React Router and plain JS equivalents — all while keeping feature parity so the migration was invisible to end users.

// result

A frontend stack consistent with the rest of the client's web properties, a more modern component architecture, and lower onboarding cost for engineers moving between the client's applications.

CASE 03 Inline SQL → stored procedures and UDTTs on MSSQL, at Keyfalcon Solutions
// problem

This client's data layer standardized on MSSQL with stored procedures rather than an ORM, but parts of the application still ran inline queries, and some business logic looped over data in application code before hitting the database — inconsistent with the client's architecture, and inefficient at scale.

// approach

Converted the inline queries into parameterized stored procedures matching the client's conventions, and re-architected the complex application-side loop logic to use MSSQL User-Defined Table Types (UDTTs) — passing structured, tabular data into a stored procedure in a single call instead of iterating and issuing repeated round trips from the application layer.

// result

Fewer database round trips, execution plans that could be cached and reused, a smaller SQL-injection surface from parameterized SPs, and a data layer consistent with how the rest of the client's systems were built.

CASE 04 A custom parent-child dropdown, and an early lesson about reaching for libraries
// problem

My first assignment as an engineer at Keyfalcon Solutions: build a custom dropdown with checkboxes supporting parent-child selection — selecting a parent should select its children, and partial child selection needed to reflect back on the parent. The obvious starting point was an off-the-shelf UI library that claimed to do exactly this.

// approach

On the surface, the third-party library looked like it worked — but once tested against the actual business rules for parent-child state, its behavior didn't fully match what was needed. That gap led me to build the component from scratch instead, which meant working through every interaction case myself: parent-to-child propagation, indeterminate states for partial selection, and edge cases the library glossed over.

// result

A working component that matched the actual requirements — and a lesson that's stuck with me since: reaching for a library that promises a quick result means first understanding its internals well enough to know where it diverges from your business needs. Otherwise something can look functional on the surface while being wrong underneath.
